> [!IMPORTANT]
> **Critical Correction vs. Erratum 1 (`UART_IIR_FCR = 0x00`):**  
> Prior silicon testing documented in [`CRITICAL_KNOWLEDGE_GAPS_AND_ASSUMPTIONS.md`](../CRITICAL_KNOWLEDGE_GAPS_AND_ASSUMPTIONS.md#L148-L153) proves THEJAS32 Synopsys DW_apb_uart hardware exhibits RX FIFO pointer/ordering corruption if `FCR = 0x07` or `0x01` is written (`Erratum 1`). Therefore, **the coding agent MUST NOT blindly enable hardware FIFOs (`FCR = 0x07`)** without re-verifying FIFO stability on silicon. Instead:
> - On **UART0 TX**, solve the `~100 B/s` bottleneck and `>= 256 B` wrap cleanly while respecting `FCR = 0x00` (raise `UART_TX_BUFFER_SIZE` to `512`, check free TX space unconditionally, fix atomic `txBufferTail`, and increase `uartPollTx()` drain cadence / bounded `THRE` wait under `Erratum 1` OR re-verify TX-only vs RX FIFO silicon erratum).
> - On **UART1 RX (CRSF @ `420,000` baud)**, recognize that `FCR = 0x00` limits hardware buffering to **1 byte (`23.8 us`)**—any `thejas32_atomic_enter()` / ISR section exceeding `~20 us` risks Overrun Error (`ORE`) and dropped RC frames.

## 4. Deep-Dive 3-Part Critique

### What Went Wrong
1. **Safety Boundary Blindness Across Reset/Panic/Continuous PWM (`#1`, `#2`, `#15`)**: Neither CPU exception handlers nor `systemReset()` shut down Timer 1 motor outputs, while `useContinuousUpdate = true` causes `1 kHz` `writeMotors()` to clobber `400 Hz` (`> 1,000 us`) ESC frames before they complete.
2. **Erratum 1 Trade-Offs Left Unresolved on Both UARTs (`#3`, `#4`, `#5`, `#7`)**: Correctly honoring `FCR = 0x00` (`Erratum 1`) kept VEGA RX keystrokes unscrambled, **but** left UART0 TX stuck at `~100 B/s` (`256 B` buffer wrapping on `306 B` `MSP_ADJUSTMENT_RANGES`) and narrowed UART1 `420k` CRSF RX tolerance to a `23.8 us` single-byte window without timing audits.
3. **Diagnostic vs. Full-Firmware Drift (`#6`, `#8`, `#12`, `#18`)**: `bootstrap_diag.c` hardcoded optimistic Phase 11–13 printouts (`16-byte FIFO`, `((void)0)`, simulated `thejas32_gpio0_isr()`), masking `.bss` config erasure, real `IRQ 10` edge/level uncertainty, and missing gyro/PID silicon timing.

### What Could Have Been Done Better
1. **Treat Cross-Module Configurator + Actuator + Sensor Bringup as Mandatory Gate Before Advancing Phases**: Testing `MSP_ADJUSTMENT_RANGES` (`306 B`), warm reboot config retention, and `1500 us` Timer 1 oscilloscope pulses inside full `TARGET=ARIESV3` catches `#1`–`#7` immediately.
2. **Avoid Stale Text Assertions in `bootstrap_diag.c`**: Measuring actual `FCR`, `ARIES_DEV_LOGGING`, hardware pin edges, and loop cycles prevents Phase 19 diagnostic logs from contradicting active code.

### What Were the Good / Brilliant Parts
1. **Clean Separation of `TARGET=ARIESV3` vs. Upstream Core**: Upstream edits stay minimal (`9` files under `mk/` and `src/main/`, `+65/-10` lines vs `885f12404`) and the `191,224 B` binary leaves `31,744 B` under `248 KB` (`25,600 B` under `0x0023E800`).
2. **Deterministic Fast Host Verification Harness**: `19` `test_aries_*` suites (`285/285` tests) run cleanly under host GCC with zero flakiness, making it straightforward to add non-mocked `msp.c` / buffer-wrap / atomic regression checks right away.
