================================================================================
How hard will this overall port be?
Overall Feasibility Rating: MODERATE (7/10 Difficulty, Very Realistic)

Why?
- The hardest architectural barrier—getting Betaflight's massive build system,
  scheduler, math libraries, parameter groups, and linker scripts to compile 
  cleanly under the non-ARM RISC-V RV32IM toolchain—is ALREADY SOLVED in Phase 2.
- The remaining work consists of standard embedded peripheral driver implementation:
  reading/writing memory-mapped hardware registers on the THEJAS32 SoC.
- Betaflight already contains sensor drivers for nearly every IMU on earth (MPU6050,
  ICM-42688, BMI270, etc.). Once we provide a working SPI byte-transfer function,
  the existing flight controller code detects and configures the sensor automatically!
- Memory limits are NOT a problem:
  * Flash: We use 708 KB out of 2,048 KB (only 34.5% used).
  * RAM: We use 63.7 KB out of 256 KB (only 24.9% used).

PHASE 3: HARDWARE UART DRIVER & BETAFLIGHT CLI / MSP (NEXT IMMEDIATE STEP)
--------------------------------------------------------------------------------
Objective:
Connect THEJAS32 UART0 peripheral to the onboard Silicon Labs CP2102N USB-UART 
bridge so that plugging the board into a PC allows interactive CLI commands
and Betaflight Configurator connection.

What To Do:
1. Implement `src/platform/ARIES/serial_uart_aries.c`:
   - Memory-mapped base address: UART0 = 0x11200000 (standard 16550/16750 layout).
   - Configure baud rate generator (100 MHz clock / (16 * Baud)).
   - Set 8 data bits, no parity, 1 stop bit (8N1).
   - Enable 16-byte TX and RX FIFOs.
2. Implement Ring Buffer & Interrupt Handler:
   - Connect UART0 RX interrupt to push received characters into Betaflight's 
     `serialPort->rxBuffer`.
   - Implement `uartWrite()` to push bytes into the TX FIFO.
3. Wire into Betaflight Serial VTable:
   - Hook `serialUART()` in `stub_drivers.c` to return a configured `uartPort_t`.
   - Hook `uartPinConfigure()` for UART0.
4. Test & Validate:
   - Connect via `picocom -b 115200 /dev/ttyUSB0`.
   - Press `#` and verify `# version`, `# status`, and `# tasks` respond in CLI.
   - Open Betaflight Configurator GUI and connect to `/dev/ttyUSB0`.

Challenges & Pitfalls:
- Baud rate clock divisor rounding error at 115200 baud on 100 MHz core.
  Formula: Divisor = 100,000,000 / (16 * 115200) = 54.25 -> Integer divisor 54
  Actual baud = 100,000,000 / (16 * 54) = 115,740 baud (0.47% error, well within 2% UART tolerance).
- Level: EASY to MODERATE (Standard 16550 UART registers).

PHASE 4: PRECISION HARDWARE TIMER & MICROSECOND CLOCK
--------------------------------------------------------------------------------
Objective:
Provide an accurate, drift-free `micros()` and `millis()` timebase required by
the flight loop scheduler.

What To Do:
1. Enhance `src/platform/ARIES/system.c`:
   - Currently, `getCycleCounter()` reads `csrr mcycle` (32-bit counter).
   - At 100 MHz, a 32-bit counter wraps around every 42.94 seconds!
   - Fix: Read 64-bit cycle counter (`mcycle` + `mcycleh` on RISC-V) or implement
     a rollover tracker to prevent scheduler glitch every 43 seconds.
   - Code pattern for 64-bit atomic CSR read on RV32:
     ```c
     uint64_t getCycleCounter64(void) {
         uint32_t h0, h1, l;
         do {
             __asm__ volatile("csrr %0, mcycleh" : "=r"(h0));
             __asm__ volatile("csrr %0, mcycle"  : "=r"(l));
             __asm__ volatile("csrr %0, mcycleh" : "=r"(h1));
         } while (h0 != h1);
         return ((uint64_t)h0 << 32) | l;
     }
     ```
2. Hardware Timer Backup:
   - Check THEJAS32 Timer 0 registers (`0x11100000`). If hardware timer generates
     periodic ticks (e.g. 1 kHz SysTick), use it for system millisecond heartbeat.
3. Test & Validate:
   - Run a 10-second delay loop and verify against real-world stopwatch.
   - Run CLI `status` and check that `Uptime` increments continuously past 60s.

Challenges & Pitfalls:
- 32-bit integer division in `micros()`: dividing uint32 by 100 takes 30-40 CPU cycles
  without hardware divider. But VEGA ET1031 has the 'M' extension (hardware divide!),
  so integer division `divu` is executed in hardware in ~32 cycles.
- Level: VERY EASY.

PHASE 5: SPI BUS DRIVER & EXTERNAL IMU INTEGRATION
--------------------------------------------------------------------------------
Objective:
Read gyro and accelerometer data from the external IMU sensor (connected via SPI 
header pins) at 1 kHz to feed the flight stabilization algorithms.

What To Do:
1. Implement `src/platform/ARIES/bus_spi_aries.c`:
   - Memory-mapped base address: SPI0 = `0x11300000`.
   - Implement `spiInitDevice()`:
     * Clock polarity (CPOL = 0) and phase (CPHA = 0) - SPI Mode 0 or Mode 3.
     * Clock prescaler: 100 MHz / 10 = 10 MHz (IMU sensors support up to 10-20 MHz).
   - Implement synchronous byte transfer:
     ```c
     uint8_t spiTransferByte(spiDevice_t *dev, uint8_t data);
     bool spiTransfer(spiDevice_t *dev, uint8_t *rx, const uint8_t *tx, size_t length);
     ```
   - Implement Chip Select (CS) toggle using GPIO.
2. Wire Target Configuration in `target.h`:
   - `#define USE_IMU_MPU6050` or `#define USE_IMU_ICM42688P` or `#define USE_IMU_BMI270`
     (matches whichever physical breakout sensor is plugged into the headers).
   - Specify SPI device and CS pin.
3. Test & Validate:
   - Read the sensor's `WHO_AM_I` register (e.g. 0x75 on MPU6000/6050 returns 0x68).
   - In Betaflight CLI, run `status` and confirm:
     `Arming disable flags: NO_GYRO` disappears and `Gyro/Acc: ICM42688P (1.00kHz)` is reported.
   - Verify live gyro/accel traces in Betaflight Configurator "Sensors" tab!

Challenges & Pitfalls:
- SPI FIFO handling: Ensure TX FIFO is drained and RX FIFO has valid data before CS goes HIGH.
- Level: MODERATE.

PHASE 6: SOFT-FLOAT MATH OPTIMIZATION & LOOP RATE TUNING
--------------------------------------------------------------------------------
Objective:
Optimize the PID and filtering calculation loop so that soft-float operations
complete well within the 1000 us (1 kHz) scheduler deadline.

What To Do:
1. Benchmark Soft-Float PID Execution Time:
   - Place cycle counter timestamps around `taskMainPidLoop()` in `fc/tasks.c`.
   - Measure average execution time (typical ARM Cortex-M4 with FPU takes ~35 us;
     RV32IM soft-float is expected to take ~150-250 us at 100 MHz).
2. Apply Optimization Flags:
   - Betaflight already uses `-ffast-math -fno-math-errno` and our custom `-DFAST_MATH`.
   - Ensure GCC soft-float library `libgcc.a` uses the integer multiplier for `__mulsf3`.
3. Loop Rate Selection:
   - 1.0 kHz loop time (`TASK_GYROPID_DESIRED_PERIOD 1000`) is ideal for RV32IM soft-float.
   - 250 us of CPU load every 1000 us = 25% CPU utilization (leaves 75% for scheduler,
     CLI, receiver, and telemetry).
4. Test & Validate:
   - Check CLI `tasks`: verify `PID loop` task rate is exactly 1000 Hz, with 0 late/missed tasks.

Challenges & Pitfalls:
- High-order dynamic notch filters (`dyn_notch_filter.c`) use trigonometric math (sinf/cosf).
  If CPU load exceeds 50%, reduce notch filter count or disable RPM filter.
- Level: EASY to MODERATE (profiling and parameter tuning).

PHASE 7: MOTOR OUTPUT DRIVERS (PWM / DSHOT)
--------------------------------------------------------------------------------
Objective:
Generate control signals for 4 Electronic Speed Controllers (ESCs) driving the quad's motors.

What To Do:
Option A: Standard PWM (50 Hz - 400 Hz) / OneShot125 (Recommended First Step)
- Use THEJAS32 hardware PWM timer channels.
- Set period to 2.5 ms (400 Hz).
- Pulse width: 1000 us (0% throttle) to 2000 us (100% throttle).
- Implement `motorPwmDevInit()` and `pwmWriteMotor()`.

Option B: DShot Digital ESC Protocol (DShot150 / DShot300)
- DShot is a digital protocol (16-bit packet sent every loop).
- On chips without DMA (like THEJAS32), DShot requires cycle-accurate GPIO bitbang.
- At 100 MHz, 1 CPU clock = 10 nanoseconds.
  * DShot150 bit time = 6.67 us (667 CPU cycles per bit).
  * Very easy to bitbang with tight assembly loop!
- Test & Validate:
  - Connect oscilloscope or logic analyzer to motor pins 1–4.
  - Test motor spinning via Betaflight Configurator "Motors" tab (props OFF!).

Challenges & Pitfalls:
- If bitbanging DShot without DMA, interrupts must be disabled during the 16-bit burst (~100 us).
- Level: Standard PWM = EASY; Bitbang DShot = MODERATE-HARD.

4. KEY TECHNICAL CHALLENGES & HOW TO SOLVE THEM
================================================================================

CHALLENGE 1: NO HARDWARE FPU (FLOATING POINT UNIT)
- Why: VEGA ET1031 is RV32IM, not RV32IMF.
- Impact: Math operations (`float a + b`, `sinf(x)`) call GCC software routines
  (`__addsf3`, `__mulsf3`).
- Solution:
  * Limit loop rate to 1.0 kHz (`TASK_GYROPID_DESIRED_PERIOD 1000`).
  * At 100 MHz, 1 ms = 100,000 clock cycles. A typical soft-float PID calculation
    consumes ~20,000 cycles, which is only 20% CPU load!
  * Keep `FAST_MATH` enabled (uses polynomial approximations for trig functions).

CHALLENGE 2: NO DIRECT ON-CHIP USB CDC CONTROLLER
- Why: Unlike STM32F405, THEJAS32 has no native USB peripheral.
- Impact: No native DFU mode or direct Virtual COM Port (VCP).
- Solution:
  * The ARIES board already incorporates an onboard Silicon Labs CP2102N USB-UART bridge.
  * The PC sees a standard USB COM port (`/dev/ttyUSB0`).
  * Betaflight CLI and Configurator communicate over this serial port transparently.

CHALLENGE 3: NO DMA CONTROLLER (OR LIMITED DMA)
- Why: Standard Betaflight targets rely heavily on STM32 DMA for SPI and DShot.
- Impact: Cannot use circular DMA buffers for SPI and serial.
- Solution:
  * Use interrupt-driven ring buffers for UART.
  * Use fast polling for SPI IMU transfers (reading 14 bytes from gyro at 10 MHz
    takes only 11.2 microseconds—doing this synchronously in the PID loop is fast).
  * Use standard PWM timer hardware for ESC control (no CPU overhead).

CHALLENGE 4: 32-BIT CYCLE COUNTER ROLLOVER (MCYCLE)
- Why: `mcycle` is a 32-bit register incrementing at 100 MHz.
- Impact: Wraps every 42.94 seconds.
- Solution:
  * Read the 64-bit pair (`mcycle` + `mcycleh`), which will not roll over for 5,849 years.
